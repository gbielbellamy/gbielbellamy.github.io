Northstar

A single workspace for running a career transition: plan the day, ship the project, track the search, and see whether any of it is working. Nine sections, one domain model, and — for now — not a single network request.

Role
Design and engineering, solo
Year
2026 — ongoing
Stack
React 19, TypeScript, Vite, Zustand, Recharts, Framer Motion
Status
Runs locally — database, accounts and login in progress

The problem

Changing careers is a project with no manager. There is a curriculum to get through, a portfolio to build, companies to research, people to contact and applications to chase — and each of those lives in a different tool that knows nothing about the others. The spreadsheet doesn't know you skipped Tuesday. The calendar doesn't know which skill that session was for. Nothing can tell you whether the whole thing is on track, because nothing sees all of it.

Northstar is the answer to a narrow question: what would it take to see the entire effort on one screen, and have it stay honest when the plan slips?

What it does

Nine sections, each one a view onto the same data rather than a separate silo.

How it's built

The architecture is one rule applied consistently: each layer only knows about the one below it.

types/ defines the domain and nothing imports upward from it. data/seed.ts is a single object matching that shape. store/ holds all state and persists it. lib/ is pure logic — plain functions, no React, no store access. Pages read from the store, call into lib/ for anything computed, and render components. Nothing in components/ reaches into the store; data arrives as props.

That last constraint is the one that pays off. Because no component can fetch its own state, every component is trivially reusable and the Components page can render the whole system in isolation. And because scheduling and funnel maths live in lib/, they can be reasoned about without mounting a single React tree.

Three decisions worth explaining

Decision 01 — Elastic scheduling

The naive version of a study planner marks a missed session as failed and moves on. That is exactly the behaviour that makes people abandon the tool in week three. In Northstar, skipping a session pushes its content to that area's next slot: the plan stretches instead of shedding work. The trade-off is that "what is scheduled today" becomes a computed value rather than a stored one, which is why it lives in lib/pacing.ts as a pure function of the plan and your history.

Decision 02 — Versioned plan, untouched history

Everything persists to localStorage, which raises an awkward question: what happens when the app ships a better roadmap to someone who already has data? The store merges on load using a planVersion field — the plan (roadmap, goals, schedule, skill paths) is replaced when the seed moves ahead, while anything the user recorded themselves is left alone. Shipping an improved plan never costs anyone their history.

Decision 03 — One definition of "today"

Date bugs are the quiet killers in any scheduling app: parse a date string as UTC in one place and as local time in another, and entries start landing on the wrong day for anyone west of Greenwich. There is exactly one definition of today and one local-midnight parser, both in lib/dates.ts, and nothing else is allowed to construct a date. For the same reason the dev port is pinned in vite.config.ts — localStorage is scoped to the origin, so a moving port would mean a moving data store.

Why it started local

Starting with a server would have been the more impressive-sounding choice and the wrong first move. A backend brings accounts, authentication, a privacy story and a hosting bill with it — all of which are real work, and none of which would have told me whether the product was any good. Keeping everything in the browser meant the questions that actually decided that — pacing, merging, the funnel model — got the time instead.

The cost is real, and the app says so plainly: data is per browser and per device, and clearing site data erases it. That is why JSON export and import sit on the Dashboard rather than buried in a settings page.

It is also why that constraint is now the thing to lift. The pure-function layer was built so the source of the data could change without the logic changing with it, and that is exactly what happens next.

What's next

Northstar runs locally today. The current work is the other half of it:

  • A PostgreSQL database behind the app, so the plan and the history stop living in one browser on one machine.
  • Accounts and login, with the security work that has to come with them — hashed credentials, protected routes, sessions that expire.
  • A public deployment, so the app can be tried rather than described.
  • Tests around lib/pacing.ts and the selectors. The pure functions were written to be testable and deserve the tests.
